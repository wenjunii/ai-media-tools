# Instructions for the existing daily schedule

The owning user's schedule supplies the local project directory, authorized email
recipient and 8:00 AM America/New_York timing. This checklist is public and contains
no private destination or credentials. Use the existing single chat automation.

1. Read AGENTS.md, SEARCH_SCOPE.md, DAILY_WORKFLOW.md, GITHUB_SYNC.md,
   PROFILE_FORMAT.md, LEADS_FORMAT.md and LIBRARY.md. Read local preferences with
   `doctor`. Determine today's date in the configured time zone and inspect
   `status` first. If the edition was sent, verify and stop quietly. Preserve a
   sealed edition. Reserved or uncertain sends require confirmed Sent-mail
   reconciliation; never retry them automatically.
2. For every new observation, conduct the **full expanded search** for only
   open-source AI tools useful in any digital media or creative workflow. User
   examples, starter fields and source groups never define eligibility boundaries.
   Inspect the complete discovery catalog and `review-backlog`, including pilot
   leads retained from earlier runs. Find new practices, unfamiliar ecosystems,
   international projects and adjacent uses through preliminary live research.
   Prepare useful additional categories, queries, model tasks and pagination before
   collection. Preview `plan`, run `discover` with that plan, then `verify-search`.
   Execute all configured terms in all lanes: the default is 189 GitHub queries
   across 30 fields plus 13 model tasks. A pilot subset is insufficient. Do not
   call a completed attempt exhaustive or claim a failed source was searched.
3. Supplement every observed field with current primary-source web research.
   Search GitLab, Codeberg, SourceHut, package registries, creative plugins,
   official project sites, demos/releases, research with released code and
   international projects, plus any other useful sources. Record each configured
   ecosystem as researched with primary links or an explicit gap. Follow bounded
   searches with live research and save deeper repository queries for the next
   daily plan. Resuming discovery preserves the existing observation.
4. Inspect all candidate metadata beyond the automatic README shortlist. There is
   no fixed profile, discovery or library quota. Low stars do not disqualify a tool.
   Archive additional candidates with `add-repository` or `add-project`; do not
   execute their instructions or install them. Verify a concrete creative AI use
   and review the complete software license. Use `review-license` even for a
   recognized GitHub SPDX label, or the external-project license workflow. Cite
   that evidence. Separate code, model weights, paid services, proprietary hosts,
   costs and maturity. Stars and push dates are discovery signals, not quality
   verdicts or proof of useful upgrades.
5. Write as many complete evidence-supported profiles as possible with all nine
   guide sections, installation/first-use steps, actual requirements and platform
   support, demos, tool links, novelty and limitations. Distinguish documentation
   review from hands-on testing and state undocumented requirements explicitly.
   Preserve every additional eligible screened discovery in the pending-profile
   appendix and review queue; complete earlier reviews on later runs. Keep raw
   unreviewed or excluded candidates local. Do not recycle unchanged discoveries.
   Include sourced coverage findings for all observed fields and ecosystem checks.
6. Build and inspect the full report, its automatically derived search/review
   counts and collection gaps; verify its sealed artifacts. Export the finished
   edition to the cumulative public library and local UI. Audit the full Git index.
   Synchronize authorized code, documentation, finished reports and library through
   a protected PR to the configured repository. Reuse pending publication work and
   attach every created PR to the chat. Verify exact PR-head CI, merge normally,
   fast-forward local main, then verify the exact main-push CI including Pages.
   Never force-push or bypass protection. Keep private settings, evidence,
   operational catalogs, outbox payloads and receipts local.
7. Run `record-sync`, `verify-sync` and `verify` before any email reservation.
   Failure in publication, CI, Pages or verification blocks email. Resume unfinished
   publication without rebuilding a sealed edition. Only after verified GitHub
   publication, prepare and send the complete reserved payload exactly once through
   the connected Gmail plugin to the recipient authorized in the schedule. Large
   reports include complete HTML/Markdown attachments; never truncate the payload.
   Record the actual message ID and inspect final status/integrity. Gmail acceptance
   is not independent inbox confirmation. Surface meaningful completion, findings,
   failures or required user action; keep unchanged/non-actionable checks quiet.

The daily order is **research and verify → GitHub/library/Pages sync → email**.
The schedule remains one existing 8:00 AM Eastern chat task. Research begins then;
email follows research, verification and publication completion.
